# Kubernetes YAML Mastery — From Memory

A pattern-based system for writing Kubernetes manifests from memory, not from Stack Overflow.

---

## 0. The Core Idea

You already know Kubernetes concepts. What's missing is **structural muscle memory** — the ability to picture the YAML tree in your head before you type anything.

The whole course rests on one claim:

> There are only a handful of *shapes*. Every manifest is one of these shapes with different labels stuck on it.

Everything below teaches you the shapes.

---

## PART 1 — The Universal Formula

Every Kubernetes object — no exceptions — is this:

```yaml
apiVersion: <group/version>
kind: <ResourceType>
metadata:
  name: <string>
spec:
  <resource-specific fields>
```

| Field | Meaning | Required? | Common to all? |
|---|---|---|---|
| `apiVersion` | Which API group/version defines this kind | Yes | Yes |
| `kind` | Which resource type | Yes | Yes |
| `metadata.name` | Object's unique name | Yes | Yes |
| `metadata.namespace` | Which namespace it lives in | No (defaults to `default`) | Yes (field exists on all namespaced objects) |
| `metadata.labels` | Key/value tags for selection | No | Yes |
| `metadata.annotations` | Key/value metadata, not used for selection | No | Yes |
| `spec` | Desired state — resource-specific | Usually yes | Yes (shape differs per kind) |
| `status` | Current observed state | Never write it | Auto-generated by the cluster, ignore when authoring |

**Mental model — "APIV-KMS":**

```
apiVersion
    ↓
kind
    ↓
metadata
    ↓
spec
    ↓
resource-specific fields
```

You never write `status`. The API server fills it in. If you find yourself typing `status:` in a manifest you're writing, stop — that's a sign you're copy-pasting a `kubectl get -o yaml` dump instead of authoring from scratch.

## PART 2 — The "4-Block" Memory System

Before writing ANY manifest, answer these four questions in order:

```
1. API    → Which apiVersion?
2. KIND   → Which resource kind?
3. META   → What name / namespace / labels?
4. SPEC   → What does this resource type need in spec?
```

```yaml
apiVersion: apps/v1        # Q1
kind: Deployment            # Q2

metadata:                   # Q3
  name: my-app
  labels:
    app: my-app

spec:                       # Q4
  ...
```

Drill this until it's reflexive: **API → KIND → META → SPEC**, always in that order, every single time you open an empty file.

## PART 3 — The Resource Family Map

Don't learn resources alphabetically. Learn them by *job*.

```
KUBERNETES RESOURCES

Workloads (run your code)
├── Pod                — one or more containers, smallest deployable unit
├── Deployment          — stateless, replicated, self-healing Pods
├── ReplicaSet          — low-level replica controller (Deployment manages this for you)
├── StatefulSet         — stateful Pods with stable identity + storage
├── DaemonSet           — one Pod per node
├── Job                 — run-to-completion task
└── CronJob             — scheduled Job

Networking (get traffic to Pods)
├── Service             — stable internal address for a set of Pods
├── Ingress             — HTTP(S) routing from outside the cluster
├── NetworkPolicy       — firewall rules between Pods
└── EndpointSlice       — low-level, usually auto-managed

Configuration (feed data into Pods)
├── ConfigMap           — non-secret config
├── Secret              — sensitive config
└── ServiceAccount      — Pod's identity for API/RBAC

Storage (persist data)
├── PersistentVolume (PV)       — actual storage resource
├── PersistentVolumeClaim (PVC) — Pod's request for storage
└── StorageClass                — how PVs get provisioned dynamically

Security / RBAC (who can do what)
├── Role / ClusterRole              — WHAT is allowed
└── RoleBinding / ClusterRoleBinding — CONNECT identity to permission

Scaling
├── HorizontalPodAutoscaler (HPA) — scale replica count
└── VerticalPodAutoscaler (VPA)   — scale resource requests/limits

Scheduling / Governance
├── PriorityClass   — Pod scheduling priority
├── ResourceQuota   — namespace-wide resource caps
├── LimitRange      — default/min/max per Pod or container
└── PodDisruptionBudget — min availability during voluntary disruption
```

Every time you learn a new resource, ask **"which family, and what job does it do?"** before learning its fields.

## PART 4 — Pod YAML (the atom everything is built from)

### Minimum viable Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  containers:
    - name: app
      image: nginx:1.27
```

That's the entire skeleton. Everything else is an addition to `spec.containers[]` or a sibling of `containers` under `spec`.

### Field-by-field (What → Why → Where → Memory trick)

| Field | What | Why | Where | Memory trick |
|---|---|---|---|---|
| `labels` | Tags for selection | Services/Deployments find Pods via labels | `metadata.labels` | "labels live where the name lives" |
| `annotations` | Non-selectable metadata | Tooling, docs, config hints | `metadata.annotations` | "notes nobody searches by" |
| `ports` | Declares container's listening port | Documentation + some tooling (not enforced) | `containers[].ports[].containerPort` | "ports sit inside the container that owns them" |
| `env` | Inline env vars | Configure app at runtime | `containers[].env[]` | "env is per-container, like a container's own shell" |
| `envFrom` | Bulk-import env vars | Avoid listing 20 vars one by one | `containers[].envFrom[]` | "FROM = whole source dumped in" |
| `command` / `args` | Override image entrypoint/cmd | Change what process runs | `containers[]` | "command = binary, args = flags" |
| `resources.requests` | Minimum guaranteed CPU/mem | Scheduling decisions | `containers[].resources.requests` | "requests = what you ask the scheduler for" |
| `resources.limits` | Hard ceiling | Prevent noisy-neighbor | `containers[].resources.limits` | "limits = the ceiling you can't break" |
| `volumeMounts` | Where a volume appears *inside* the container | Container's filesystem view | `containers[].volumeMounts[]` | "mount = the container's plug" |
| `volumes` | Where the data actually comes from | Pod-level storage source | `spec.volumes[]` (sibling of containers) | "volumes = the pod's socket, mounts = the container's plug" |
| `probes` | Health checks | Restart/traffic decisions | `containers[].livenessProbe` / `readinessProbe` / `startupProbe` | see Part 21 |
| `securityContext` | Run-as-user, capabilities, etc | Hardening | Both `spec.securityContext` (Pod-wide) and `containers[].securityContext` (per-container override) | "Pod sets the default, container can override" |
| `serviceAccountName` | Which identity the Pod uses | RBAC / API access | `spec.serviceAccountName` | "Pod-level, sibling of containers" |
| `nodeSelector` | Simple node picking | Constrain scheduling | `spec.nodeSelector` | "the blunt instrument" |
| `affinity` | Advanced node/pod attraction-repulsion | Fine-grained placement | `spec.affinity` | "the scalpel" |
| `tolerations` | Allow scheduling onto tainted nodes | Opt-in to restricted nodes | `spec.tolerations` | "tolerate the taint" |
| `initContainers` | Run-to-completion setup containers | Prep work before main containers start | `spec.initContainers[]` | "init = before the party starts" |
| `lifecycle` | postStart / preStop hooks | Graceful startup/shutdown actions | `containers[].lifecycle` | "hooks around the container's life" |
| `terminationGracePeriodSeconds` | How long to wait before SIGKILL | Graceful shutdown window | `spec.terminationGracePeriodSeconds` | "Pod-level, not per container" |

### Pod tree (full picture)

```
Pod
├── apiVersion
├── kind
├── metadata
│   ├── name
│   ├── namespace
│   ├── labels
│   └── annotations
└── spec
    ├── serviceAccountName
    ├── nodeSelector / affinity / tolerations
    ├── securityContext            (Pod-wide defaults)
    ├── terminationGracePeriodSeconds
    ├── initContainers[]
    │   └── (same shape as containers)
    ├── containers[]
    │   ├── name
    │   ├── image
    │   ├── command / args
    │   ├── ports[]
    │   ├── env[] / envFrom[]
    │   ├── resources.requests / limits
    │   ├── volumeMounts[]
    │   ├── livenessProbe / readinessProbe / startupProbe
    │   ├── securityContext        (per-container override)
    │   └── lifecycle
    └── volumes[]                  (Pod-level source of truth)
```

**Rule to memorize: "Volumes are declared once at the Pod level; they're mounted per-container."** This is the #1 source of confusion — people try to put `volumes:` inside a container.

## PART 5 — The Container Block (memorize this shape cold)

```yaml
spec:
  containers:
    - name:
      image:
      ports:
      env:
      resources:
      volumeMounts:
```

```
spec
 └── containers[]              (a LIST — always starts with "- ")
      └── one container
           ├── name             (required, unique within Pod)
           ├── image             (required)
           ├── ports[]
           ├── env[]
           ├── resources
           │   ├── requests
           │   └── limits
           ├── volumeMounts[]
           ├── livenessProbe / readinessProbe
           └── securityContext
```

**Indentation rule:** `containers` is a **list**, so every item starts with `- `. Everything belonging to *that* container is indented consistently under the `-`. This is where 90% of beginner YAML bugs live — an `env:` block accidentally indented one space off, landing as a sibling of the container instead of a child.

## PART 6 — Deployment YAML

### Skeleton

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
        - name: my-app
          image: my-app:1.0
```

### The one idea that unlocks everything

```
Deployment
    ↓  (manages)
selector          — "which Pods do I own?"
    ↓  (must match labels of)
template.metadata.labels
    ↓  (template IS a Pod spec)
template.spec
    ↓
containers
```

**Deployment = replicas + selector + template.**

`template` is *literally a Pod definition* minus `apiVersion`/`kind` (because it's implied). If you already know Pod YAML, you already know 80% of Deployment YAML — you're just nesting it one level deeper under `spec.template`.

### Tree

```
Deployment
├── apiVersion: apps/v1
├── kind: Deployment
├── metadata
│   ├── name
│   └── labels
└── spec
    ├── replicas
    ├── selector
    │   └── matchLabels   (must equal template.metadata.labels)
    ├── strategy
    │   ├── type: RollingUpdate | Recreate
    │   └── rollingUpdate
    │       ├── maxUnavailable
    │       └── maxSurge
    ├── minReadySeconds
    ├── revisionHistoryLimit
    ├── progressDeadlineSeconds
    └── template                  ← a Pod spec, nested
        ├── metadata
        │   └── labels            (must match selector.matchLabels)
        └── spec
            └── containers[]
```

### Advanced fields, quick reference

| Field | Meaning | Memory trick |
|---|---|---|
| `strategy.rollingUpdate.maxUnavailable` | How many Pods can be down during update | "how far can it dip" |
| `strategy.rollingUpdate.maxSurge` | How many extra Pods above `replicas` during update | "how far can it bulge" |
| `minReadySeconds` | How long a new Pod must stay Ready before counted "available" | "cooldown before trusted" |
| `revisionHistoryLimit` | How many old ReplicaSets to keep for rollback | "how far back you can undo" |
| `progressDeadlineSeconds` | Timeout before rollout is marked Failed | "patience limit" |

**Why `selector` exists separately from `template.metadata.labels`:** the selector is *immutable* after creation and is how the Deployment finds "its" Pods (including ones it didn't just create, e.g. after a controller restart). The template labels are what get *stamped onto* new Pods. They must overlap or the Deployment can never adopt/manage anything — this mismatch is one of the most common real-world bugs.

## PART 7 — Service YAML

### Skeleton

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app
spec:
  selector:
    app: my-app
  ports:
    - port: 80
      targetPort: 8080
```

### Mental model

```
Service
 ↓ (selects)
Pod labels          — "who am I sending traffic to?"
 ↓
port                — "what port do I, the Service, expose?"
 ↓
targetPort          — "what port does the container actually listen on?"
```

**`port` vs `targetPort` vs `nodePort`, in one line each:**
- `port` — the port *other things in the cluster* use to reach this Service.
- `targetPort` — the port *on the container* traffic actually gets forwarded to.
- `nodePort` — the port opened *on every node's IP* (only for `type: NodePort`), 30000–32767 by default.

### Types

```yaml
spec:
  type: ClusterIP      # default — internal only
  type: NodePort        # ClusterIP + exposed on every node's IP:nodePort
  type: LoadBalancer     # NodePort + cloud provider provisions an external LB
  type: ExternalName     # DNS CNAME to an external name, no proxying
```

### Headless Service

```yaml
spec:
  clusterIP: None
  selector:
    app: my-db
```
No load-balancing IP — DNS returns each Pod's IP directly. Used by StatefulSets for stable per-Pod addressing.

### Named / multiple ports

```yaml
spec:
  selector:
    app: my-app
  ports:
    - name: http
      port: 80
      targetPort: 8080
      appProtocol: http
    - name: metrics
      port: 9090
      targetPort: 9090
```
`name` becomes required as soon as you have more than one port.

### sessionAffinity

```yaml
spec:
  sessionAffinity: ClientIP
```
Pins a client to the same backend Pod based on source IP.

## PART 9 — ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  APP_ENV: production
  LOG_LEVEL: info
  application.conf: |
    server.port=8080
    server.timeout=30
```

`data` holds **either** short literal values **or** whole file contents (using `|` block scalar) — same field, two use-cases.

### As environment variables — bulk

```yaml
containers:
  - name: app
    envFrom:
      - configMapRef:
          name: app-config
```

### As environment variables — single key

```yaml
containers:
  - name: app
    env:
      - name: APP_ENV
        valueFrom:
          configMapKeyRef:
            name: app-config
            key: APP_ENV
```

### As a mounted file

```yaml
containers:
  - name: app
    volumeMounts:
      - name: config-vol
        mountPath: /etc/app
volumes:
  - name: config-vol
    configMap:
      name: app-config
```

**env vs volume, one sentence:** env vars are read once at container start and can't change without a restart; a mounted ConfigMap file is kept in sync live (with a short delay) if the ConfigMap changes.

## PART 10 — Secret

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-credentials
type: Opaque
data:
  username: YWRtaW4=      # base64 of "admin"
stringData:
  password: supersecret    # plaintext — k8s base64-encodes it for you at apply time
```

- `data` — values must be **base64-encoded by you**.
- `stringData` — values are **plaintext**; the API server encodes them on write. Convenient for authoring, but the resulting object still only stores base64 (not encryption).

**Base64 is encoding, not encryption** — anyone with read access to the Secret object (or etcd, if unencrypted at rest) can trivially decode it. For real protection use encryption-at-rest, an external secret manager (Vault, AWS Secrets Manager, Sealed Secrets, External Secrets Operator), and tight RBAC on `get`/`list` for Secrets.

Common `type` values:

| type | Use |
|---|---|
| `Opaque` | Generic (default) |
| `kubernetes.io/dockerconfigjson` | Private registry credentials |
| `kubernetes.io/tls` | TLS cert + key (`tls.crt`, `tls.key`) |
| `kubernetes.io/basic-auth` | username/password |
| `kubernetes.io/service-account-token` | Legacy SA tokens |

Usage in a Pod mirrors ConfigMap exactly: `envFrom.secretRef`, `env[].valueFrom.secretKeyRef`, or `volumes[].secret`.

## PART 12 — Ingress

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app
spec:
  ingressClassName: nginx
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: my-app
                port:
                  number: 80
```

### Hierarchy

```
Ingress
 └── spec
      ├── ingressClassName
      ├── tls[]
      │    ├── hosts[]
      │    └── secretName
      └── rules[]
           └── host
                └── http
                     └── paths[]
                          ├── path
                          ├── pathType   (Exact | Prefix | ImplementationSpecific)
                          └── backend
                               └── service
                                    ├── name
                                    └── port.number
```

### Multiple hosts / paths / TLS

```yaml
spec:
  ingressClassName: nginx
  tls:
    - hosts: ["myapp.example.com"]
      secretName: myapp-tls
  rules:
    - host: myapp.example.com
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service: { name: api-svc, port: { number: 80 } }
          - path: /
            pathType: Prefix
            backend:
              service: { name: web-svc, port: { number: 80 } }
    - host: admin.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service: { name: admin-svc, port: { number: 80 } }
```

**pathType — Exact vs Prefix:** `Exact` matches the path literally, character for character. `Prefix` matches on `/`-separated path segments (`/api` matches `/api` and `/api/anything`, not `/apixyz`).

**Ingress resource vs Ingress Controller:** the Ingress **resource** is just a declaration of routing rules — inert on its own. The Ingress **Controller** (nginx-ingress, Traefik, AWS ALB controller, etc.) is the actual running software that watches Ingress objects and configures a real load balancer/proxy accordingly. No controller installed → Ingress objects do nothing.

## PART 13 — Storage: PV, PVC, StorageClass

```
StorageClass
     ↓ (used by dynamic provisioner referenced in)
PersistentVolumeClaim.spec.storageClassName
     ↓ (triggers creation of, or binds to an existing)
PersistentVolume
     ↓ (consumed by, via claimName)
Pod.spec.volumes[].persistentVolumeClaim.claimName
```

### PersistentVolumeClaim (the one you'll write most often)

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
  storageClassName: standard
```

### Using it in a Pod

```yaml
containers:
  - name: app
    volumeMounts:
      - name: data
        mountPath: /var/lib/data
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: data-pvc
```

### PersistentVolume (usually admin-authored or dynamically created — you rarely hand-write this)

```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-example
spec:
  capacity:
    storage: 10Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: standard
  hostPath:
    path: /data
```

### StorageClass

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard
provisioner: kubernetes.io/aws-ebs
parameters:
  type: gp3
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

**Memorize the chain, not the individual YAML:** `StorageClass → dynamic provisioning → PV → PVC → Pod`. In cloud clusters you almost never write PV or StorageClass by hand — you write the PVC and reference an existing StorageClass.

## PART 14 — StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  serviceName: db-headless
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: db
          image: postgres:16
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 20Gi
```

```
StatefulSet
 ↓
Headless Service (serviceName)     — gives each Pod a stable DNS name: db-0.db-headless, db-1.db-headless...
 ↓
Stable network identity            — Pod name is always <name>-<ordinal>, survives rescheduling
 ↓
Persistent storage (per-Pod)       — volumeClaimTemplates create one PVC per Pod, reused across restarts
```

Key fields beyond Deployment's shape:
- `serviceName` — must point at a **headless** Service (`clusterIP: None`).
- `podManagementPolicy` — `OrderedReady` (default, sequential start) or `Parallel`.
- `updateStrategy` — similar to Deployment's `strategy`, defaults to `RollingUpdate` but updates Pods in reverse ordinal order.
- `volumeClaimTemplates` — replaces the plain `volumes` reference; StatefulSet generates one PVC per replica automatically (`data-db-0`, `data-db-1`, ...).

## PART 15 — DaemonSet

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      containers:
        - name: agent
          image: node-agent:1.0
```

Same `selector` + `template` shape as Deployment — **no `replicas` field**, because DaemonSet runs exactly one Pod per matching node, always.

**Deployment vs StatefulSet vs DaemonSet, one memory line each:**
- Deployment → "I don't care which Pod, I just want N of them" (interchangeable).
- StatefulSet → "I care about *which one* — each has its own name and disk" (identity matters).
- DaemonSet → "I want it on every node" (topology matters, not count).

## PART 16 — Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 3
  activeDeadlineSeconds: 300
  ttlSecondsAfterFinished: 3600
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: migrate
          image: migrate-tool:1.0
```

| Field | Meaning |
|---|---|
| `completions` | How many successful Pod completions are needed |
| `parallelism` | How many Pods run at once |
| `backoffLimit` | Retries before marking Job failed |
| `activeDeadlineSeconds` | Overall timeout for the whole Job |
| `ttlSecondsAfterFinished` | Auto-delete the Job (and Pods) N seconds after completion |
| `restartPolicy` | Must be `Never` or `OnFailure` — **never `Always`** inside a Job's Pod template |

## PART 17 — CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: nightly-backup
spec:
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: backup-tool:1.0
```

```
CronJob
 ↓
schedule            (standard cron syntax)
 ↓
jobTemplate          (an entire Job.spec, nested)
 ↓
Job                  (created automatically on each trigger)
 ↓
Pod
 ↓
Container
```

Memorize this as "a Job wrapped in a schedule, wrapped in a CronJob" — three layers of `spec` deep before you hit `containers`.

## PART 18 — RBAC

Mental model:

```
WHO?      → ServiceAccount
WHAT?     → Role (namespaced) / ClusterRole (cluster-wide)
CONNECT?  → RoleBinding / ClusterRoleBinding
```

### ServiceAccount

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
```

### Role

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: configmap-reader
  namespace: default
rules:
  - apiGroups: [""]
    resources: ["configmaps"]
    verbs: ["get", "list", "watch"]
```

### RoleBinding

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: app-can-read-configmaps
  namespace: default
subjects:
  - kind: ServiceAccount
    name: app-sa
    namespace: default
roleRef:
  kind: Role
  name: configmap-reader
  apiGroup: rbac.authorization.k8s.io
```

`ClusterRole` / `ClusterRoleBinding` are the same shapes, minus `namespace` (they're cluster-scoped). A `ClusterRoleBinding` can also bind a `ClusterRole` to subjects across all namespaces, and a `RoleBinding` can reference a `ClusterRole` to grant its permissions *within one namespace only* — a very common production pattern (define reusable ClusterRoles, bind them per-namespace).

**RBAC tree:**

```
Role / ClusterRole
 └── rules[]
      ├── apiGroups[]     ("" = core API group)
      ├── resources[]
      └── verbs[]          (get, list, watch, create, update, patch, delete)

RoleBinding / ClusterRoleBinding
 ├── subjects[]
 │    ├── kind    (ServiceAccount | User | Group)
 │    ├── name
 │    └── namespace
 └── roleRef
      ├── kind
      ├── name
      └── apiGroup
```

## PART 19 — NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-to-backend
spec:
  podSelector:
    matchLabels:
      app: backend
  policyTypes:
    - Ingress
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - protocol: TCP
          port: 8080
```

Mental model:

```
WHO?              → podSelector           (which Pods this policy applies to)
WHAT TRAFFIC?     → policyTypes: [Ingress, Egress]
FROM WHERE?       → ingress[].from[]      (podSelector / namespaceSelector / ipBlock)
TO WHERE?         → egress[].to[]
WHICH PORT?       → ports[]
```

**Default-deny all ingress in a namespace:**

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-ingress
spec:
  podSelector: {}     # empty selector = applies to ALL pods in namespace
  policyTypes:
    - Ingress
```

**Allow egress only to DNS + a specific namespace:**

```yaml
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - namespaceSelector:
            matchLabels:
              kubernetes.io/metadata.name: kube-system
      ports:
        - protocol: UDP
          port: 53
```

Rule to remember: **an empty `podSelector: {}` means "all Pods."** An empty `ingress: []` with `policyTypes: [Ingress]` present means "deny all ingress" (because no rule ever matches).

## PART 20 — Resource Management

```yaml
containers:
  - name: app
    resources:
      requests:
        cpu: "250m"
        memory: "256Mi"
      limits:
        cpu: "500m"
        memory: "512Mi"
```

- **requests** = what the scheduler reserves for this container on a node; also the floor guaranteed to it.
- **limits** = the hard ceiling; CPU gets throttled above limit, memory gets the container OOM-killed above limit.

`ResourceQuota` (namespace-wide cap) and `LimitRange` (default/min/max per Pod/container if unspecified) live one level up:

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
spec:
  hard:
    requests.cpu: "10"
    requests.memory: 20Gi
    limits.cpu: "20"
    limits.memory: 40Gi
```

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-limits
spec:
  limits:
    - default:
        cpu: "500m"
        memory: "512Mi"
      defaultRequest:
        cpu: "250m"
        memory: "256Mi"
      type: Container
```

## PART 21 — Health Checks

```
Startup     → "has the app finished booting yet?" (blocks the other two probes while running)
   ↓
Readiness   → "is it currently able to serve traffic?" (controls Service endpoints)
   ↓
Liveness    → "is it stuck/dead and needs a restart?" (controls container restarts)
```

```yaml
containers:
  - name: app
    startupProbe:
      httpGet:
        path: /startupz
        port: 8080
      failureThreshold: 30
      periodSeconds: 5
    readinessProbe:
      httpGet:
        path: /readyz
        port: 8080
      periodSeconds: 5
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      periodSeconds: 10
      failureThreshold: 3
```

Probe mechanisms:

```yaml
httpGet:
  path: /healthz
  port: 8080
tcpSocket:
  port: 5432
grpc:
  port: 9090
exec:
  command: ["cat", "/tmp/healthy"]
```

Use `startupProbe` for slow-booting apps (JVM, big migrations) so `livenessProbe` doesn't kill the container mid-boot. Use `readinessProbe` for anything with warm-up/dependency checks. `livenessProbe` should be simple and cheap — it decides whether to kill the container.

## PART 22 — Security Context

```yaml
spec:
  securityContext:              # Pod-wide defaults
    runAsUser: 1000
    runAsGroup: 1000
    runAsNonRoot: true
    fsGroup: 2000
  containers:
    - name: app
      securityContext:          # per-container override
        allowPrivilegeEscalation: false
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]
        seccompProfile:
          type: RuntimeDefault
```

`spec.securityContext` (Pod level) sets identity/fsGroup defaults inherited by all containers. `containers[].securityContext` (container level) can override those and adds container-only settings (`capabilities`, `allowPrivilegeEscalation`, `readOnlyRootFilesystem`). Memory hook: **"identity is Pod-wide, capabilities are per-container."**

## PART 23 — Scheduling

```yaml
spec:
  nodeSelector:
    disktype: ssd

  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values: ["ssd"]
    podAntiAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 100
          podAffinityTerm:
            labelSelector:
              matchLabels:
                app: my-app
            topologyKey: kubernetes.io/hostname

  tolerations:
    - key: "dedicated"
      operator: "Equal"
      value: "gpu"
      effect: "NoSchedule"

  topologySpreadConstraints:
    - maxSkew: 1
      topologyKey: topology.kubernetes.io/zone
      whenUnsatisfiable: DoNotSchedule
      labelSelector:
        matchLabels:
          app: my-app

  priorityClassName: high-priority
```

Memory hooks:
- `nodeSelector` — blunt, exact-match only.
- `nodeAffinity` — nodeSelector with `required`/`preferred` and operators (`In`, `NotIn`, `Exists`...).
- `podAffinity` / `podAntiAffinity` — "stick near" / "stay away from" other Pods.
- `tolerations` — cancels out a node's `taint`; taint says "keep out," toleration says "except me."
- `topologySpreadConstraints` — spread Pods evenly across zones/nodes.

## PART 24 — Autoscaling (HPA)

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
    - type: Resource
      resource:
        name: memory
        target:
          type: Utilization
          averageUtilization: 80
```

```
HPA
 ↓
scaleTargetRef        — points at the Deployment/StatefulSet it controls
 ↓
minReplicas/maxReplicas — the bounds
 ↓
metrics[]              — what triggers scaling (cpu, memory, or custom/external metrics)
```

Custom metric example:
```yaml
metrics:
  - type: Pods
    pods:
      metric:
        name: requests_per_second
      target:
        type: AverageValue
        averageValue: "100"
```
HPA requires the target Deployment to already declare `resources.requests` for CPU/memory metrics to work — no requests, no percentage to compute against.

## PART 26 — Labels & Selectors (the connective tissue of Kubernetes)

```
LABEL                  (arbitrary key/value stamped on an object)
  ↓
SELECTOR               (a query: "give me everything with these labels")
  ↓
RESOURCE CONNECTION     (controller/Service/policy now "owns" or "targets" those objects)
```

```yaml
# On the Pods (via template):
metadata:
  labels:
    app: nginx
    tier: frontend

# On the thing that finds them:
selector:
  matchLabels:
    app: nginx
```

Where selectors show up:

| Resource | Selects |
|---|---|
| Deployment/StatefulSet/DaemonSet | Pods it manages (`spec.selector.matchLabels`) |
| Service | Pods it load-balances to (`spec.selector`) |
| NetworkPolicy | Pods the policy applies to (`spec.podSelector`) — plus separate selectors for `from`/`to` peers |
| PersistentVolumeClaim | Optionally, a specific PV (`spec.selector`) |
| HPA | Not a selector — it uses `scaleTargetRef` by name instead |

**Common mismatch exercise:** spot the bug.

```yaml
# Deployment
spec:
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: webapp     # <-- BUG: doesn't match selector above
```
This fails to create — Kubernetes rejects a Deployment whose `selector` doesn't match its own `template.metadata.labels`.

```yaml
# Service
spec:
  selector:
    app: web
    tier: frontend       # <-- Pods only have "app: web", missing "tier" label
```
This *doesn't error* — it silently results in a Service with **zero endpoints**. Always check `kubectl get endpoints <svc>` when a Service "isn't working."

## PART 28 — The Pod Template Master Pattern

This single shape reappears inside every workload controller:

```yaml
template:
  metadata:
    labels:
      app: <app>
  spec:
    containers:
      - name: <app>
        image: <image>
```

It appears at:

| Resource | Location |
|---|---|
| Deployment | `spec.template` |
| StatefulSet | `spec.template` |
| DaemonSet | `spec.template` |
| Job | `spec.template` |
| CronJob | `spec.jobTemplate.spec.template` (one level deeper, nested inside a Job spec) |

**Once you know Pod YAML, you know the payload of every controller.** The only thing that changes between controllers is what wraps *around* `template` (`replicas`+`selector` for Deployment, `serviceName`+`volumeClaimTemplates` for StatefulSet, nothing extra for DaemonSet, `completions`/`backoffLimit` for Job, `schedule` for CronJob).

## PART 30 — `kubectl explain` as Your Memory Tool

This is your real "documentation," faster than a web search, and it works offline.

```bash
kubectl explain deployment
kubectl explain deployment.spec
kubectl explain deployment.spec.template
kubectl explain deployment.spec.template.spec.containers
kubectl explain deployment.spec.template.spec.containers.resources.requests
kubectl explain pod.spec.containers.livenessProbe --recursive
```

**Method to reconstruct a manifest when you blank on a field:**
1. Start typing what you *do* remember (the 4-block skeleton).
2. Where you're unsure of a nested field, run `kubectl explain <kind>.<path>` for that exact path.
3. `--recursive` dumps the whole subtree instantly if you've forgotten the shape entirely.

**Rule: don't memorize every field — memorize the *structure*, and know how to discover fields in 5 seconds.** Nobody in production recalls every `securityContext.capabilities` field from memory; they recall that it exists under `containers[].securityContext` and run `kubectl explain` to get the exact spelling.

## PART 38 — Production-Grade Deployment (worked example)

Everything from Parts 4–24 combined into one realistic manifest:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api
  namespace: production
  labels:
    app: api
    app.kubernetes.io/part-of: platform
spec:
  replicas: 3
  revisionHistoryLimit: 5
  progressDeadlineSeconds: 300
  selector:
    matchLabels:
      app: api
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  template:
    metadata:
      labels:
        app: api
    spec:
      serviceAccountName: api-sa
      terminationGracePeriodSeconds: 30
      securityContext:
        runAsNonRoot: true
        runAsUser: 1000
        fsGroup: 2000
      containers:
        - name: api
          image: myregistry/api:1.4.2
          ports:
            - containerPort: 8000
          envFrom:
            - configMapRef:
                name: api-config
            - secretRef:
                name: api-secrets
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
          readinessProbe:
            httpGet: { path: /readyz, port: 8000 }
            periodSeconds: 5
          livenessProbe:
            httpGet: { path: /healthz, port: 8000 }
            periodSeconds: 10
            failureThreshold: 3
          securityContext:
            allowPrivilegeEscalation: false
            readOnlyRootFilesystem: true
            capabilities:
              drop: ["ALL"]
      affinity:
        podAntiAffinity:
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchLabels: { app: api }
                topologyKey: kubernetes.io/hostname
```

```
Ingress            → routes host/path to a Service
   ↓
Service            → load-balances to Pods via label selector
   ↓
Deployment          → manages replicated Pods
   ↓
Pods
   ↓
ConfigMap / Secret   → injected as env or volumes
   ↓
Persistent Storage   → only if the workload is stateful (often a StatefulSet instead)
```

## 1. Active Recall Drill Bank

Organized by topic. Answer out loud or on paper before expanding.

### 1.1 — The Universal Formula & 4-Block System

<details><summary>Q1. What are the four blocks, in order, that every manifest starts with?</summary>API → KIND → META → SPEC (apiVersion, kind, metadata, spec)</details>
<details><summary>Q2. Which field should you never hand-write in a manifest?</summary><code>status</code> — it's populated by the cluster, not the author.</details>
<details><summary>Q3. Is `metadata.namespace` required?</summary>No — defaults to <code>default</code> if omitted (for namespaced resources only; cluster-scoped kinds like Node, ClusterRole, PV don't have it at all).</details>
<details><summary>Q4. Name three fields under `metadata` besides `name`.</summary><code>namespace</code>, <code>labels</code>, <code>annotations</code></details>

### 1.2 — Pod & Container Block

<details><summary>Q5. Is `containers` a list or a map? What syntax gives it away?</summary>A list — each entry starts with <code>- </code>.</details>
<details><summary>Q6. Where do `volumes` live vs `volumeMounts`?</summary><code>volumes</code>: Pod level (<code>spec.volumes</code>, sibling of <code>containers</code>). <code>volumeMounts</code>: per-container (<code>containers[].volumeMounts</code>).</details>
<details><summary>Q7. Where does `command` go, and what does it override?</summary">Inside a container block (<code>containers[].command</code>); overrides the image's ENTRYPOINT.</details>
<details><summary>Q8. What's the difference between `env` and `envFrom`?</summary><code>env</code> sets one variable at a time (with optional valueFrom); <code>envFrom</code> bulk-imports every key from a ConfigMap/Secret as env vars.</details>
<details><summary>Q9. Where do `initContainers` run relative to `containers`?</summary>Before — sequentially, and must all complete successfully before any main container starts.</details>
<details><summary>Q10. Where does `terminationGracePeriodSeconds` belong — Pod or container level?</summary>Pod level (<code>spec.terminationGracePeriodSeconds</code>).</details>

### 1.3 — Deployment

<details><summary>Q11. Write the three things that define a Deployment, one word each.</summary>replicas + selector + template</details>
<details><summary>Q12. What must `selector.matchLabels` equal?</summary><code>template.metadata.labels</code> — must match, or the object is rejected at creation.</details>
<details><summary>Q13. Where does `maxSurge` live, and what does it control?</summary><code>spec.strategy.rollingUpdate.maxSurge</code> — how many extra Pods above <code>replicas</code> are allowed during a rollout.</details>
<details><summary>Q14. What's the difference between `strategy.type: Recreate` and `RollingUpdate`?</summary><code>Recreate</code> kills all old Pods before creating new ones (downtime); <code>RollingUpdate</code> replaces Pods incrementally (no full downtime).</details>

### 1.4 — Service

<details><summary>Q15. Define `port` vs `targetPort` vs `nodePort` in one line each.</summary><code>port</code>=what other cluster clients use to reach the Service; <code>targetPort</code>=the container's actual listening port; <code>nodePort</code>=port opened on every node's IP (NodePort type only).</details>
<details><summary>Q16. How do you make a Service headless, and why would you?</summary><code>spec.clusterIP: None</code> — used so DNS resolves to individual Pod IPs instead of a load-balanced VIP (StatefulSets rely on this).</details>
<details><summary>Q17. What silently breaks if a Service's selector doesn't match any Pod labels?</summary>The Service creates successfully but has zero Endpoints — traffic goes nowhere, no error is raised.</details>

### 1.5 — ConfigMap / Secret

<details><summary>Q18. `data` vs `stringData` in a Secret — what's the difference?</summary><code>data</code> values must be pre-base64-encoded by you; <code>stringData</code> takes plaintext and the API server encodes it on write.</details>
<details><summary>Q19. Is base64 encryption?</summary>No — it's just encoding. Anyone with read access can trivially decode it.</details>
<details><summary>Q20. Name the three ways a ConfigMap's data can reach a container.</summary><code>envFrom</code> (bulk env vars), <code>env[].valueFrom.configMapKeyRef</code> (single env var), or mounted as a file via <code>volumes</code>+<code>volumeMounts</code>.</details>

### 1.6 — Ingress

<details><summary>Q21. What's the nesting path from Ingress spec down to a Service port?</summary><code>spec.rules[].host → http.paths[] → path/pathType → backend.service.name + port.number</code></details>
<details><summary>Q22. Ingress resource vs Ingress Controller — what's the difference?</summary">The resource is just a declared routing rule (inert alone); the Controller is the running software (nginx, Traefik, ALB) that actually implements it.</details>
<details><summary>Q23. `Prefix` vs `Exact` pathType — explain the difference.</summary><code>Exact</code> matches the literal path only; <code>Prefix</code> matches on path segments, so <code>/api</code> also matches <code>/api/anything</code>.</details>

### 1.7 — Storage

<details><summary>Q24. Recite the storage chain from provisioning to Pod.</summary>StorageClass → dynamic provisioning → PersistentVolume → PersistentVolumeClaim → Pod</details>
<details><summary>Q25. What field in a Pod references a PVC?</summary><code>spec.volumes[].persistentVolumeClaim.claimName</code></details>
<details><summary>Q26. What StatefulSet field replaces a plain PVC reference, and why?</summary><code>volumeClaimTemplates</code> — because each replica needs its own uniquely-named PVC, not a shared one.</details>

### 1.8 — RBAC

<details><summary>Q27. State the WHO / WHAT / CONNECT model.</summary>WHO=ServiceAccount, WHAT=Role/ClusterRole, CONNECT=RoleBinding/ClusterRoleBinding</details>
<details><summary>Q28. Can a RoleBinding reference a ClusterRole? Why would you do that?</summary">Yes — to reuse one set of permissions (defined once as a ClusterRole) but grant it scoped to a single namespace via a namespaced RoleBinding.</details>
<details><summary>Q29. What are the four fields inside an RBAC `rules[]` entry?</summary><code>apiGroups</code>, <code>resources</code>, <code>verbs</code> (and optionally <code>resourceNames</code>)</details>

### 1.9 — NetworkPolicy

<details><summary>Q30. What does an empty `podSelector: {}` mean?</summary>Applies to all Pods in the namespace.</details>
<details><summary>Q31. How do you write a "default deny all ingress" policy?</summary><code>podSelector: {}</code>, <code>policyTypes: [Ingress]</code>, and no <code>ingress</code> rules (or an empty list) — no rule ever matches, so nothing is allowed in.</details>

### 1.10 — Probes, Security, Scheduling, Scaling

<details><summary>Q32. Order the three probe types by "boot → serve → survive."</summary>startupProbe → readinessProbe → livenessProbe</details>
<details><summary>Q33. Which probe controls whether a Pod receives Service traffic?</summary>readinessProbe</details>
<details><summary>Q34. Pod-level vs container-level securityContext — what's the rule of thumb?</summary>Identity defaults (runAsUser, fsGroup) at Pod level; container-only knobs (capabilities, readOnlyRootFilesystem, allowPrivilegeEscalation) at container level.</details>
<details><summary>Q35. `taint` vs `toleration` — who "wins"?</summary">A taint on a node repels Pods by default; a matching toleration on a Pod cancels that repulsion for that Pod specifically.</details>
<details><summary>Q36. What must a Deployment already declare for CPU-based HPA to work?</summary><code>resources.requests.cpu</code> — HPA computes utilization as a percentage of the request.</details>
<details><summary>Q37. What field does HPA use to find its target — a selector or something else?</summary><code>scaleTargetRef</code> (kind+name), not a label selector.</details>

## 2. Broken-YAML Debugging Set

Ten manifests, each with 2–6 real bugs (syntax, indentation, wrong field location, mismatched selectors, deprecated API, invalid values). Find them all before expanding the answer.

### Debug 1 — Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: webapp
    spec:
    containers:
      - name: web
        image: nginx:1.27
        ports:
        - containerPort: 80
        resources:
          requests:
          cpu: 100m
          memory: 128Mi
```

<details><summary>Answer</summary>

1. `template.metadata.labels.app: webapp` ≠ `selector.matchLabels.app: web` → object rejected at creation. Fix: make them match.
2. `containers:` is indented at the same level as `spec:` under template — should be indented one level *into* `spec:` (`spec:\n  containers:`).
3. `cpu: 100m` is indented as a sibling of `requests:` instead of a child — should be nested under `requests:`.
4. (Minor but worth flagging) No `limits` block — not a hard error, but a production-readiness gap.
</details>

### Debug 2 — Service

```yaml
apiVersion: v1
kind: Service
metadata:
  name: web-svc
spec:
  selector:
    app: web-app
  ports:
    - port: 80
    targetPort: 80
```

<details><summary>Answer</summary>

1. `targetPort` is indented as a sibling of the ports list item instead of a child of it — should be nested under the same `- port: 80` entry.
2. `selector.app: web-app` likely doesn't match the Pods' actual label (`app: web`, per Debug 1) — silently zero endpoints. Verify against the real Pod labels.
</details>

### Debug 3 — ConfigMap + env injection

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  - APP_ENV: production
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: app
spec:
  containers:
    - name: app
      image: app:1.0
      envFrom:
        - configMapRef: app-config
```

<details><summary>Answer</summary>

1. `data:` is a map, not a list — remove the leading `-`. Should be `data:\n  APP_ENV: production`.
2. `containers` is placed directly under `Deployment.spec` — missing `selector` and `template` entirely; a Deployment cannot have `containers` directly under `spec`.
3. `configMapRef: app-config` should be `configMapRef:\n    name: app-config` — it needs a `name` key, not a bare string.
</details>

### Debug 4 — PVC + Pod

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessMode: ReadWriteOnce
  resources:
    requests:
      storage: 10Gi
---
apiVersion: v1
kind: Pod
metadata:
  name: db
spec:
  containers:
    - name: db
      image: postgres:16
      volumeMounts:
        - name: data
          mountPath: /var/lib/postgresql/data
  volumes:
    - name: data
      persistentVolumeClaim:
        name: data-pvc
```

<details><summary>Answer</summary>

1. `accessMode` should be `accessModes` (plural) and its value must be a list: `accessModes: ["ReadWriteOnce"]`.
2. `volumes[].persistentVolumeClaim` needs the key `claimName`, not `name`: `persistentVolumeClaim:\n    claimName: data-pvc`.
</details>

### Debug 5 — Ingress

```yaml
apiVersion: extensions/v1beta1
kind: Ingress
metadata:
  name: web
spec:
  rules:
    - host: web.example.com
      http:
        paths:
          - path: /
            backend:
              serviceName: web-svc
              servicePort: 80
```

<details><summary>Answer</summary>

1. `apiVersion: extensions/v1beta1` is deprecated/removed — should be `networking.k8s.io/v1`.
2. `pathType` is missing — required in `networking.k8s.io/v1` (must be `Exact`, `Prefix`, or `ImplementationSpecific`).
3. `backend.serviceName`/`servicePort` is the old v1beta1 shape — in `networking.k8s.io/v1` it's `backend.service.name` and `backend.service.port.number`.
</details>

### Debug 6 — RBAC

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: core
    resources: pods
    verbs: get, list
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: bind-pod-reader
subjects:
  - kind: ServiceAccount
    name: app-sa
roleRef:
  kind: Role
  name: pod-reader
```

<details><summary>Answer</summary>

1. `apiGroups: core` is wrong — the core API group is represented as an empty string: `apiGroups: [""]`.
2. `resources: pods` and `verbs: get, list` must be lists: `resources: ["pods"]`, `verbs: ["get", "list"]`.
3. `subjects[].namespace` is missing for the ServiceAccount — required to disambiguate which namespace's SA is meant.
4. `roleRef` is missing `apiGroup: rbac.authorization.k8s.io` — required field.
5. `RoleBinding.metadata.namespace` is missing — a RoleBinding must live in the same namespace as the Role it references (here, `default`).
</details>

### Debug 7 — NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
spec:
  podSelector:
    app: backend
  ingress:
    - from:
        - podSelector:
            app: frontend
      port: 8080
```

<details><summary>Answer</summary>

1. `spec.podSelector` needs a `matchLabels` key — it's not a bare label map: `podSelector:\n    matchLabels:\n      app: backend`.
2. Same issue inside `from[].podSelector` — needs `matchLabels`.
3. `policyTypes: [Ingress]` is missing entirely — without it, behavior is ambiguous/implicit and best practice requires declaring it explicitly.
4. `port: 8080` should be `ports:\n    - port: 8080` (list, plural key, and typically includes `protocol`).
</details>

### Debug 8 — HPA

```yaml
apiVersion: autoscaling/v1
kind: HorizontalPodAutoscaler
metadata:
  name: app-hpa
spec:
  scaleTargetRef:
    kind: Deployment
    name: app
  minReplicas: 10
  maxReplicas: 3
  targetCPUUtilizationPercentage: 70
```

<details><summary>Answer</summary>

1. `minReplicas: 10` > `maxReplicas: 3` — logically invalid, min must be ≤ max.
2. `scaleTargetRef` is missing `apiVersion: apps/v1`.
3. Using `autoscaling/v1` with `targetCPUUtilizationPercentage` works, but it's the old shape — modern manifests should use `autoscaling/v2` with a `metrics[]` list for multi-metric and custom-metric support.
</details>

### Debug 9 — StatefulSet

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
spec:
  replicas: 3
  selector:
    matchLabels:
      app: db
  template:
    metadata:
      labels:
        app: db
    spec:
      containers:
        - name: db
          image: postgres:16
  volumeClaimTemplates:
    - metadata:
        name: data
      spec:
        accessModes: ["ReadWriteOnce"]
        resources:
          requests:
            storage: 20Gi
```

<details><summary>Answer</summary>

1. `spec.serviceName` is missing entirely — **required** for StatefulSet; must point at a headless Service that governs the network identity of the Pods.
</details>

### Debug 10 — CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: 0 2 * * *
  jobTemplate:
    metadata:
      labels:
        app: backup
    spec:
      restartPolicy: Always
      containers:
        - name: backup
          image: backup:1.0
```

<details><summary>Answer</summary>

1. `schedule: 0 2 * * *` should be quoted: `schedule: "0 2 * * *"` — unquoted, YAML may misparse the cron string.
2. `jobTemplate.spec` is missing the nested `template:` layer — should be `jobTemplate.spec.template.spec.containers`, not `jobTemplate.spec.containers` directly. CronJob → Job spec → Pod template → Pod spec is three layers.
3. `restartPolicy: Always` is invalid inside a Job/CronJob Pod template — must be `Never` or `OnFailure`.
</details>
